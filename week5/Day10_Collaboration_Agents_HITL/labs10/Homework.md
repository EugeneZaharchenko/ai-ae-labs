## Що ви отримаєте

`ADK 2.0 Collaborative Workflow Engine` — багатоагентна система на **справжній моделі** (Ollama / Gemini / OpenAI — через `internal/modelcfg`):

- спеціалісти — `llmagent` із `functiontool`, кожен у власній під-гілці (контекст сусідів йому не видно);
- fan-out на три гілки → `workflow.NewJoinNode` → зведення в детермінованому порядку;
- координатор, що формулює підсумок і **називає прогалину**, а не згладжує її;
- затвор схвалення: ран стає на паузу, **пауза переживає рестарт процесу**, рішення (хто/що/коли) пишеться в журнал;
- стримування збою: джерело мовчить → розділ стає прогалиною з причиною, і людина бачить це в доказі;
- відмова, мовчання (таймаут) і нерозпізнана відповідь — три різні записи; дія без схвалення не виконується ніколи.

Перший рядок має стати `модель: … → …`. Далі подивіться, як росте система: `go run .` (один спеціаліст), а решту додасте за TODO.

## Основне завдання

**Ваше завдання —** зібрати команду, яка делегує, паралелить і зупиняється перед ризиковою дією. Стартуйте з [`labs10/main.go`](https://github.com/dimetron/ai-ae-labs/blob/main/week5/Day10_Collaboration_Agents_HITL/labs10/main.go) (там уже один спеціаліст з інструментом і вибором моделі), еталон публікується після дедлайну:

1. **Команда (30).** Координатор + три спеціалісти. Кожен спеціаліст — `llmagent` з **власним** `functiontool` і власною фікстурою джерела; відповідає лише фактами з інструмента, кожен факт із ідентифікатором джерела. Поясніть у README, чому спеціалістів три, а не один (спеціалізація доменів/інструментів/контексту) і коли один агент кращий.
2. **Fan-out / fan-in (20).** Гілки паралельно; `workflow.NewJoinNode` збирає результати; порядок розділів береться з плану, не з ітерації мапи. Тест: JoinNode чекає на ВСІ гілки (скелет `TestJoinNodeWaitsForAllBranches`).
3. **Затвор схвалення (15).** `workflow.NewEmittingFunctionNode` + `workflow.ResumeOrRequestInput`, `RerunOnResume`. У питанні людині — **факти**: дія, отримувачі, хеш документа, діф, факти ризику, джерела (не проза координатора). Рішення пишіть у журнал (`labs10/internal/approvals` дано) і читайте звідти. Покажіть сценарій: `start` в одному процесі → `decide` в іншому.
4. **Вікно рішення: мовчання = відмова (5).** Прострочене питання стає `timed_out` з названою причиною. Тест із коротким вікном (десятки мс). «Людина відмовила», «людини не було», «UI надіслав незрозуміле» — три різні записи.
5. **Трасування (10).** README: фрагмент подій одного рану (хто що викликав, де пауза, які гілки паралельні) і вивід `audit`.
6. **Стримування збою (у критерії 1 і 3).** Зробіть так, щоб джерело `integration_desk` не відповідало: розділ стає прогалиною, вона видна в доказі для людини, документ не вигадується. Тест: `TestSpecialistFailureDoesNotCorruptTheAnswer`.
7. **Облік токенів.** Надрукуйте `prompt / output / total` по авторах із `UsageMetadata` подій (для офлайн-фейка — чесне «модель не повернула UsageMetadata»).

Перевірка перед здачею:

```bash
gofmt -l . ; go vet ./... ; go test -race ./...
LAB_LIVE=1 go test -run Live -v .   # опційно: потребує робочого провайдера
```

Живий тест без провайдера **пропускається з названою причиною** — «skip» не означає «пройшло»; запишіть у README, чи ви його запускали.

## Альтернативні теми (на вибір)

Та сама механіка (координатор + single_turn + task + JoinNode + HITL), інший домен:

- **Security:** координатор аудиту — спеціаліст-сканер залежностей + спеціаліст-ревʼюер конфігів працюють паралельно; HITL перед «створити тікет із критичною вразливістю».
- **Research:** міні-дослідницька група — два пошуковці по різних джерелах + збирач структурованих фактів; HITL перед фінальним звітом.
- **Fun:** турагенція з прикладу `multiagent/collaboration` (travel_planner) — погодник + букер квитків; HITL перед «оплатою» квитка.

## ++ Advanced (до 20 балів, для сеньйорів)

- Інтегруйте Fault-Tolerant Tool Harness із ДЗ 8 в інструменти спеціалістів; продемонструйте відновлення після збою всередині делегованої задачі.
- `BeforeToolCallback` як policy-точка: блокуйте виклик «ризикового» інструмента для ролей, яким це заборонено (імітація OPA / Cedar; повноцінна реалізація — поза межами курсу).
- **Чесна межа HITL:** додайте в README абзац, який описує, *як би* ви переробили HITL-паузу через Temporal для сценарію, де пауза триває 12+ годин і може пережити crash worker.

## 🔥 Бонус-трек (не оцінюється, не потрібен для сертифіката)

A2A-аутентифікація для зовнішнього підагента — з бонус-треку лекції (Блок 4): додайте в `notifyBoard` перевірку, що *тільки* авторизований coordinator викликає відправку, і опишіть у README, де в реальній системі стояли б SPIFFE/SPIRE, AAuth чи OPA/Cedar («authn + authz на кожному делегуванні»; не передавайте дочірньому агенту повний токен координатора — confused deputy). **Не додає балів і не є передумовою сертифіката** — це портфоліо-артефакт для тих, хто хоче зазирнути далі, поза межі курсу.

## Якщо щось не працює

| Симптом | Найімовірніша причина | Що зробити |
|---|---|---|
| Перший рядок «ОФЛАЙН-ФЕЙК …» | провайдера не налаштовано | вкажіть ключ у `apps/.env` або `DEFAULT_MODEL_PROVIDER=ollama`; фейк чесно названо — це не помилка |
| Ollama: `connection refused` на 11434 | демон не запущено | `ollama serve`; `curl localhost:11434/api/tags` має відповісти |
| `API key not valid` / 400 | ключ невалідний | перевірте ключ у консолі провайдера; до виправлення працюйте на офлайн-фейку |
| `dial tcp … i/o timeout` одразу після `go build` | macOS Little Snitch / фаєрвол блокує свіжий бінарник | дозвольте бінарник у фаєрволі; `curl` тим часом працює — це не баг коду |
| `go build` падає з помилкою версії | Go старіший за 1.27 | `go version`; оновіть Go |
| `запит на схвалення без конкретного доказу: документ без жодного розділу; …` | усі спеціалісти впали — причини перелічені в самій помилці | прочитайте причини після `;` (ключ, мережа, таймаут) |
| Затвор «висить» і нічого не відбувається | рішення нема; це штатна пауза | `go run . pending`, потім `decide <id> approve`; або `sweep` після закінчення вікна |
| `JoinNode` не активується | `AddFanIn` не перелічує всіх попередників | звірте ребра зі своїм `NewEngine`: `AddFanIn` має перелічити ВСІ вузли-попередники |
| Спеціаліст «відповів», але розділу немає | модель не викликала інструмент → відповідь без заземлення = прогалина | це очікувана поведінка стримування; посильте інструкцію (інструмент першим) |

## Критерії оцінювання

| Критерій | Бали |
|---|---|
| Координатор + три спеціалісти (`llmagent` + `functiontool`, заземлені відповіді, ізоляція контексту) + стримування збою | 30 |
| Паралельний fan-out із `JoinNode`-агрегацією (`NewJoinNode` + `AddFanOut` / `AddFanIn`) | 20 |
| Затвор схвалення: доказ-факти, пауза переживає рестарт, журнал хто/що/коли (сценарії approve / reject) | 15 |
| Вікно рішення: default-deny по таймауту + тест «мовчання = відмова з причиною» | 5 |
| Трасування рану по подіях + вивід `audit` + README з поясненням | 10 |
| ++ Advanced («+20 додаткових балів»: tool harness, policy-точка, Temporal-межа) | 20 |
| **Разом** | **100** |

Базове завдання дає до 80 балів; ++ Advanced — до 20 балів (разом 100). 🔥 Бонус-трек не оцінюється. Альтернативна тема оцінюється за тими самими критеріями. Бали за всі 12 завдань підсумовуються: від 60 % відкривається генерація сертифіката, від 85 % — з відзнакою.

## Формат здачі

GitHub-репозиторій / PR (основа фінального портфоліо-репозиторію багатоагентної системи); `go build ./...` має проходити; посилання на репозиторій — у форму здачі. Якщо репозиторій закритий — додайте акаунт ментора в collaborators (акаунт указано в інструкції до курсу на платформі). README повинен містити:

- короткий опис архітектури (хто координатор, хто спеціалісти, які режими, які схеми);
- фрагмент event log одного повного рану (включно з HITL-паузою) із поясненням кожного рядка;
- абзац про чесну межу HITL: «де б я зупинився на ADK, а де пішов би в Temporal»;
- секцію «що я свідомо залишив на потім» — наприклад, A2A для зовнішніх підагентів, durable execution, multi-critic цикл.
