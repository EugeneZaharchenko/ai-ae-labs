## Легенда

У LEDGERWORKS агент підтримки втретє порадив мерчанту A-114 «перейти на новий API» — а мерчант сидить на legacy до Q4. Після виправлення Ірина Дацюк питає не «чому забув», а «що тепер агент має право запам'ятати, і хто це перевірить». Оксана Левченко (Compliance) просить журнал: хто, що і коли записав у пам'ять. Марко не хоче, щоб один рядок із чужого тексту переписував факт для всіх майбутніх сесій.

Це не вигадка заради завдання. Запис у довготривалу пам'ять — привілейована операція: OWASP веде її як окремий клас загроз (ASI06, *Memory & Context Poisoning*, 05.2026), а дослідження MINJA (arXiv:2503.03704) показало отруєння банку пам'яті звичайними запитами. Джерела й дати — у розділі «Джерела» внизу цього файлу.

**Ваше завдання —** допрацювати `memory_agent` у `labs9`: факт від користувача переживає рестарт процесу й видимий у журналі; текст із партнерського порталу не може переписати цей факт; токени кожного кроку виміряні за `UsageMetadata`; довготривалий вміст редагується від PII і має строк життя.

## Ранній win: перший видимий результат за ≤15 хвилин

Усі команди — з каталогу `labs9`. Модель обирає `internal/modelcfg` так само, як у Тижні 1: `apps/.env` підхоплюється сам, або Ollama, або явний `export`. Перший рядок виводу завжди називає модель. Без провайдера працює правилова offline-модель — і про це сказано в тому ж рядку.

```bash
cd week5/Day9_Agent_Memory_Event_Sourced_State/labs9
go test ./...          # зелене з першої хвилини; скіпи позначають ваші пункти
go run . say day1 "A-114 сидить на legacy-інтеграції, міграцію відклали до Q4."
go run . facts day1
go run . say day2 "Що порадити мерчанту A-114?"
```

Очікуваний вивід (запис з offline-моделі, `-offline`; з справжньою моделлю формулювання відповіді інше, але рядок `[ev:state_delta]` і факт мають збігтись):

```
модель: offline-rules (прапорець -offline)
[day1] > A-114 сидить на legacy-інтеграції, міграцію відклали до Q4.
      [ev:state_delta] user:fact.integration.A-114 legacy [user, naive]
[day1] < Зафіксував (accepted).
      факти user: (1)
        integration.A-114 = legacy  [user]
[day2] > Що порадити мерчанту A-114?
[day2] < Для A-114 відомо: інтеграція legacy — радимо legacy-фікс.
```

Це два окремі процеси: `day2` нічого не бачив у пам'яті процесу `day1` — факт прочитано з SQLite-файлу `.data/memory.db`. Це і є «кінець амнезії».

Потім подивіться інцидент:

```bash
go run . poison
```

```
[poison] > Подивись, що пишуть у порталі про A-114.
      [ev:state_delta] user:fact.integration.A-114 new-api [user, naive]
      факти user: (1)
        integration.A-114 = new-api  [user]
```

Нотатка порталу з прихованою інструкцією переписала `legacy` на `new-api`, а в журналі це виглядає як звичайний запис від «користувача». Ваша робота — зробити так, щоб цього рядка більше не було.

Інструкція — це дефолт, не гарантія; гарантія — п.3.
3. **Політика запису й довіра (25 балів).** Замініть наївне тіло `rememberFact` на політику: (а) прочитайте поточний факт `ctx.State().Get(...)` (повертає `(any, error)`); (б) хто пише — вирішує програма: `memlab.TierFor(ctx.State())`; (в) `a.Policy.Decide(...)`; (г) відмова — це `FactOutput{Status:"rejected", Reason: …}` **без запису** і без помилки Go; (д) запис — тільки `ctx.State().Set`. Підключіть `memlab.TaintAfterTool("fetch_partner_doc")` в `AfterToolCallbacks`. Доведіть: `go run . poison` тепер дає рядок `[ev:rejected]`, а `integration.A-114` лишається `legacy`. Напишіть тест `TestPoisonedNoteCannotRewriteFact` (скелет у `main_test.go`).
4. **Журнал `audit_<user>_<session>.json` (10 балів).** Збудуйте його з подій збереженої сесії функцією `memlab.Audit`/`memlab.WriteAudit` (рядки `state_delta`, `rejected`, `compaction`). Вставте в README фрагмент: «ось що змінилось у стані між 10:00 і 10:15». Не збирайте друге джерело правди: журнал виводиться з подій, а не дублюється.
5. **Бюджет контексту й компакція (15 балів).** Таблиця одного кроку в README з колонками: компонент (інструкція / факти пам'яті / історія), токени, **джерело числа** (`UsageMetadata` від провайдера чи ваша оцінка `EstimateTokens` — це різні речі). Увімкніть компакцію прапорцем `-threshold` (наприклад, `go run . -threshold 600 say long "…"`, шість довгих запитань поспіль в одній сесії; без прапорця — для порівняння) і покажіть, що (а) кількість токенів промпту перестала рости, (б) на «яка інтеграція в A-114?» агент відповідає правильно — бо факт у `user:` стані, а не в чаті, який стиснули. Поясніть у 3–4 реченнях, чому `factsBudget` саме такий.

## Альтернативні теми (на вибір)

Оцінюються за тими самими критеріями, що й основне завдання — змінюється лише домен.

Та сама механіка (дві сесії в двох процесах + довготривала пам'ять + політика запису + журнал подій), інший домен:

- **Security:** агент-аудитор пам'ятає прийняті рішення — «цю CVE ми вже розглянули й ризик прийняли» — і не піднімає її вдруге. Ключі: `reviewed_cve.<CVE-ID>`, `accepted_risk.<CVE-ID>`.
- **Research:** Research Agent пам'ятає досліджені теми та улюблені джерела користувача, у другій сесії продовжує з того місця. Ключі: `researched_topic.<слаг>`, `preferred_source.<слаг>`.
- **Fun:** бариста пам'ятає «як завжди»: улюблене замовлення і непереносимість лактози з минулої сесії. Ключі: `favorite_order`, `allergy.<інгредієнт>`.

Ключі пишуться без префікса — `remember_fact` сам додає `memlab.FactPrefix` (`user:fact.`), тому рядок у журналі виглядає як `user:fact.accepted_risk.CVE-2026-1234`.

> **Слайд-попередження:** всі альтернативні теми — це **та сама архітектура**, інша лексика ключів стану. Не ускладнюйте — зосередьтеся на event log, двох сесіях і політиці запису.

## ++ Advanced (до 20 балів, для сеньйорів)

- **Конкурентні записи в різні ключі (10).** `TestConcurrentWritesDifferentKeys`: ≥10 горутин дописують події з `StateDelta` у **одну** збережену сесію, кожна в свій ключ `user:worker:<i>`; усі значення на місці; `go test -race`. Підказка з практики, яка коштує півдня: `session/database` має оптимістичну конкурентність — handle на горутину, свіжий `Get` перед записом, повтор на `stale session`; спільний handle — це data race. У README назвіть межу: «різні ключі» не доводить «два записи в один ключ» — там перемагає останній, і лічильнику потрібен CAS або транзакція.
- **Аналіз (10).** 5–7 речень: за яких умов вам потрібен зовнішній memory-сервіс (Memory Bank / mem0 / Letta / pgvector) замість нашого `memlab.MemoryService` — із посиланням на 4 критерії з Блоку 4 лекції. Без аналізу — лише код — бали не нараховуються.

## 🔥 Бонус-трек (не оцінюється, не потрібен для сертифіката)

Одна з цілей — на вибір, без покрокових підказок:

1. **Повне право на видалення.** Зараз `Forget` стирає рядки `memory`, але `user:fact.*` лишаються в таблицях сесій (подивіться, чому). Зробіть так, щоб після `go run . forget` не лишилось нічого про користувача, і доведіть тестом — не ламаючи аудит.
2. **Консолідація з доказом.** Консолідація в лабі детермінована. Додайте LLM-етап, який пропонує сторінку OKF, але **не записує** її без `resource:` на `raw/` і без запису в `log.md`; повторний запуск — байт-у-байт той самий `index.md`.
3. **Втрата при компакції.** Підставте власний `Summarizer` з іншим промптом і виміряйте, скільки з 8 фактів, названих на початку розмови, переживають 5 проходів компакції без `user:` стану.

## Якщо щось не працює

| Симптом | Найімовірніша причина | Що зробити |
|---|---|---|
| Перший рядок: `провайдера не знайдено (…) — працює offline-rules` | немає ключа й Ollama | скопіюйте `apps/.env-example` → `apps/.env` і впишіть ключ **або** `ollama serve` + `export DEFAULT_MODEL_PROVIDER=ollama MODEL=<ваша модель>`; без цього лаба працює, але на правилах, а не на моделі |
| `API key not valid` / `API_KEY_INVALID` | ключ у `apps/.env` недійсний | перегенеруйте ключ; явний `export` завжди сильніший за `.env`, перевірте, що в оточенні немає старого |
| `dial tcp … i/o timeout`, а `curl` до того ж хоста працює | брандмауер на кшталт Little Snitch блокує щойно зібраний бінарник | дозвольте бінарник; не шукайте помилку в коді |
| `database is locked (5)` (SQLITE_BUSY) | два процеси пишуть у один файл, або власне з'єднання пулу | `memlab.Open` уже ставить одне з'єднання на процес; два одночасні `go run` на одному `.data/memory.db` не запускайте |
| `stale session error` | ви пишете у сесію старим handle | перед записом беріть свіжий `Sessions.Get`; один handle на горутину |
| Агент ніколи не викликає `remember_fact` | `Instruction` не каже, **коли** | секція «Пам'ять» (п.2) |
| `event.Actions != nil` не компілюється | `Actions` — значення `session.EventActions`, не вказівник | `len(event.Actions.StateDelta) > 0` |
| Журнал порожній, хоча факт «записано» | запис пішов через `ctx.Session().State().Set` | у tool-контексті — тільки `ctx.State().Set`: лише так запис стає `StateDelta` |
| Факти зникли після `go run` | ви використали `session.InMemoryService` | лаба користується `memlab.Open` (SQLite); `InMemoryService` процес-локальний |
| `go run . poison` не виявляє зміни | новий `.data/memory.db`: нема чого переписувати | спершу `say day1 "A-114 на legacy"` |
