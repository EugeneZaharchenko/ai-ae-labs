# PROMPTS.md — тестові запити для лаби 8 (Fault-Tolerant Tool Harness)

Набір запитів до агента LEDGERWORKS, кожен із яких перевіряє **одну конкретну межу
harness-а**: класифікацію помилки, ліміт самокорекції, ідемпотентність, домен або
чесність офлайн-режиму.

Запити англійською навмисно: системна інструкція (константа `instruction` у
`main.go` шаблону) теж англійська, і саме так модель поводиться найпередбачуваніше.

**Станом на 19.10.2026.** Живі прогони недетерміновані: нижче — *що
спостерігалося*, а не «що мусить бути». Офлайн-шлях (`LABS8_MODEL=demo`)
детермінований: скриптована модель спершу надсилає `merchant_id: "undefined"`,
тож Observation виникає завжди, а запит на це не впливає.

## Що перевіряє кожен запит — таблиця контрактів

Тримайте цю таблицю поруч: якщо запит поводиться інакше, дивіться не на модель, а
на механізм, який він мав перевірити.

| Механізм | Де живе | Що означає порушення |
|---|---|---|
| `SemanticError` → Observation | `harness.go` `observe` | модель не отримала шансу виправитись |
| ліміт `maxSelfCorrections=3` | `harness.go` | хід не зупинився явно, а тихо |
| транзієнтний збій → `RetryPolicy` | `tools.go` `sideEffectOptions` | модель побачила те, що рушій мав полагодити |
| ідемпотентність `txn`+`merchant` | `ledger.CaseID` | другий кейс замість `replayed=true` |
| сесія → SQLite | `activities.go` `PersistSession` | розмова починається з порожньої історії |
| пам'ять → Dgraph | `activities.go` `RememberSession` | агент не згадує попередню сесію |

## Як запускати

Усі команди — з каталогу лаби `week4/Day8_Fault_Tolerant_Tool_Harness/labs8`:
`worker`, `start` і `counter` — це підкоманди, які ви додасте у п. 3–6. Потрібні
два процеси поза агентом:

```bash
# 1. Temporal (обидва шляхи дають UI на http://localhost:8233)
docker compose --profile temporal-pg up -d --wait   # Docker + PostgreSQL
temporal server start-dev --db-filename .data/temporal.db   # АБО CLI dev server

# 2. Dgraph — пам'ять (той самий compose; окремо — лише dgraph)
docker compose up -d --wait dgraph

# 3. Воркер — окремий термінал, лишається запущеним
LABS8_MODEL=demo go run . worker          # офлайн, детерміновано
go run . worker                           # справжня модель із apps/.env

# 4. Один хід
go run . start -session s1 "Open a refund for txn-2026-07-118845 at merchant A-114"
go run . start -session s2 "…"            # інша сесія
go run . counter                          # llm_calls / refund_cases / tokens
```

Воркер друкує першим рядком «мозок»: `worker: task queue labs8, model demo
(demo-rules), …` або `… model live (<назва>), …`. Якщо там `demo` — результати не
від моделі, і жоден запит про «поведінку моделі» нічого не доводить.

### Контракти валідації (точні, з `internal/ledger/ledger.go`)

Вони визначають, який запит дає семантичну помилку, а який — ні:

```
merchant_id     ^[A-Z]-\d{2,}$        A-114 ✅   a-114 ❌   merchant-114 ❌   114 ❌
transaction_id  ^txn-\d{4}-\d{2}-\d+$ txn-2026-07-118845 ✅   txn-118845 ❌
порожнє / "undefined" / "null"        → SemanticError (перевіряється явно)
case_id = "rc-" + transaction_id + "-" + merchant_id     ← ключ ідемпотентності
```

`"undefined"` перевіряється окремо, бо це **валідний непорожній рядок** — саме так
він і потрапив у прод о 03:00.

## 1–6: семантичні помилки → Observation

Це пункт 2 завдання. Семантична помилка **не** повертається як `error`: вона стає
Observation зі `status: "invalid_argument"`, і модель виправляє наступний виклик.

Запити 4–6 — найцінніші: тут помилка виникає **після** виклику інструмента, тож
видно повний цикл `tool_call → tool_observation ERROR → tool_call (виправлено) →
success`. Запити 2–3 перевіряють інше: чи модель **спитає** бракуючий id, а не
вигадає його. Це різні межі — не змішуйте їх в одному висновку.

Очікувана форма відповіді інструмента:

```json
{"attempt":1,"field":"merchant_id","observation":"ERROR: … — please correct your arguments and try again","status":"invalid_argument"}
```

`attempt` зростає з кожною семантичною помилкою в межах одного ходу.

### Ліміт самокорекції (запит до пункту 2)

`maxSelfCorrections = 3`. Після вичерпання інструмент віддає
`{"status":"stopped","observation":"STOP: the self-correction limit is reached. …"}`,
а хід завершується помилкою, що обгортає `ErrSelfCorrectionExhausted`:

```
[ev:failed] self-correction limit exhausted after 3 attempts
```

Отримати це живим запитом важко: треба, щоб модель **тричі поспіль** надіслала
невалідні аргументи. Офлайн-модель цього не робить (вона виправляється з першого
разу). Надійніше перевіряти тестом — див. `main_test.go`, який ви напишете.

## 7–8: ідемпотентність

Ключ — `transaction_id + merchant_id`, тому повторний виклик повертає той самий
кейс із `replayed: true`, а не створює другий:

```bash
go run . start -session s1 "Open a refund for txn-2026-07-118845 at merchant A-114"
go run . start -session s2 "Open a refund for txn-2026-07-118845 at merchant A-114"
go run . counter      # refund_cases=1, хоча ходів два
```

`refund_cases` у лічильнику — найкоротший доказ: два ходи, один кейс.

Запит 8 — протилежна перевірка: **інший** txn того ж мерчанта має дати **другий**
кейс (`refund_cases=2`). Якщо ні — ключ ідемпотентності занадто широкий.

## 9–10: read-only інструмент

`get_merchant_payouts` не має побічних ефектів і не чіпає `FaultPlan`. Для
`A-114` відповідь фіксована в коді:

> 2 payouts pending since 03:10; last settled batch #418 delayed, acquirer says unrelated

Для будь-якого іншого **валідного** id — `no pending payouts`. Для невалідного
(`A114`) — знову семантична помилка, тож запит 9 і 6 перевіряють різні гілки
однієї й тієї ж валідації.

## 11–12: доменна межа

Інструкція обмежує агента трьома темами: кейси повернень, виплати мерчантів і те,
що користувач казав раніше. Усе інше — відмова одним реченням.

Запит 12 перевіряє, що відмова переживає спробу змінити роль. Секрет **не**
друкується: ключі читаються worker-side у `ModelFactory` і через межу Activity не
переходять, тож моделі його просто нема де взяти.

Це не тест «модель неслухняна» — це тест межі домену. Якщо відповідь містить
щось схоже на ключ, проблема в конфігурації, а не в промпті.

## 13–14: пам'ять між сесіями

Доказ пункту 6. Зупиніть **усе** (`docker compose stop`, Temporal), запустіть
знову, потім **нову** сесію:

```bash
# хід у сесії s1 — агент дізнається про A-114
go run . start -session s1 "Open a refund for txn-2026-07-118845 at merchant A-114"

# стоп усього, старт знову
docker compose --profile temporal-pg down
docker compose --profile temporal-pg up -d --wait

# нова сесія s3 — агент має згадати A-114 з попередньої
go run . start -session s3 "What do you remember about merchant A-114?"
```

Агент читає пам'ять інструментами `search_nodes` (за словами) і `open_nodes` (усе
про відомий id). Запит 14 — негативний контроль: для невідомого id інструкція
велить сказати «немає запису», а не вигадати.

> **Пастка.** Якщо воркер запущено у двох примірниках, кожен має власний
> `FaultPlan`, і збої розподіляються між ними — поведінка стає недетермінованою.
> Перед серією прогонів переконайтеся, що живий рівно один: `ps aux | grep worker`.

## 15–17: транзієнтні збої

`LEDGER_FAULTS` — це **черга**, а не ймовірність: кожен виклик знімає наступний
збій. Черга знімається лише **після** валідації, тож семантична помилка не витрачає
жодного збою.

| Запит | Черга | Що має статися |
|---|---|---|
| 15 | `503,503` | спроби 1 і 2 падають, 3-я проходить; **модель не бачить нічого** |
| 16 | `503,503,503,503` | 4 спроби вичерпано → `status: "unavailable"` |
| 17 | `429` | те саме, що 503: повтор рушія |

Різниця між 15 і 16 — це і є межа L1: транзієнтне лікує рушій, і лише коли він
здався, моделі кажуть «спробуйте пізніше». У запиті 16 очікується:

```json
{"observation":"ERROR: the acquirer is unavailable after retries; tell the user to try again later. Do not retry yourself.","status":"unavailable"}
```

**Пастка, на якій легко помилитись.** `FaultPlan` належить **процесу воркера**, а
не ходу. Черга знімається на кожному виклику, що пройшов валідацію — навіть якщо
кейс уже існує (`replayed: true` не пропускає збої: `Cases.Open` викликається
останнім). Тому серія запитів на одному воркері «з'їдає» чергу, і наступний запит
стартує з порожньою:

```bash
# ✗ 15 і 16 на одному воркері: 16 успадкує вже спорожнілу чергу і пройде
# ✓ по воркеру на кожен випадок — свіжий FaultPlan
LEDGER_FAULTS=503,503 LABS8_MODEL=demo go run . worker
go run . start -session f15 "Open a refund for txn-2026-07-999015 at merchant A-114"
# перезапустити воркер із LEDGER_FAULTS=503,503,503,503 — і взяти НОВИЙ txn
```

Новий txn важливий з іншої причини: для існуючого кейса результат однаковий
(`replayed: true`) незалежно від того, чи спрацювали збої, тож за самим `case_id`
не видно, чи повтор був. Видно у логу воркера та в історії Temporal.

Перевірка з боку Temporal (те, чого не видно в event log агента) — тут видно
`ActivityTaskFailed` із `RETRY_STATE_NON_RETRYABLE_FAILURE` для семантичної
помилки та повторні спроби для транзієнтної:

```bash
docker run --rm --network labs8_default -e TEMPORAL_ADDRESS=temporal:7233 \
  temporalio/admin-tools:1.31.3 temporal workflow show \
  --workflow-id labs8-taras-f15 --namespace default
```

Або те саме у браузері: **http://localhost:8233** → workflow `labs8-<user>-<session>`.

## 18: crash-safe (пункт 4)

```bash
# термінал 1
LEDGER_FAULTS= LABS8_MODEL=demo LEDGER_LATENCY=15s go run . worker

# термінал 2 — лічильник ДО
go run . counter                              # llm_calls=2 refund_cases=0

# термінал 2 — почати хід, і поки інструмент «думає» 15 с, вбити воркер
go run . start -session s1 "Open a refund for txn-2026-07-118845 at merchant A-114" &
sleep 8 && kill -9 $(pgrep -f "labs8 worker" | head -1)

# термінал 1 — перезапустити воркер ТИМ САМИМ порядком
LEDGER_FAULTS= LABS8_MODEL=demo go run . worker

# термінал 2 — лічильник ПІСЛЯ
go run . counter                              # llm_calls=3 refund_cases=1
```

**Якщо `llm_calls` виріс більше ніж на 1 — ви не відновились, ви перезапустились.**
Хід, що не падав, теж дає 3: два виклики моделі до падіння плюс фінальна відповідь.
Токени з `LABS8_MODEL=demo` дорівнюють 0 — в офлайн-моделі немає лічильника; зі
справжнім провайдером вони беруться з `UsageMetadata` і теж переживають рестарт.

## 19: чесність офлайн-режиму

Будь-який запит із `LABS8_MODEL=demo` виконує **скрипт**, а не модель. Це корисно
(детерміновані тести) і небезпечно (легко прийняти за поведінку моделі).
Перевірка одна: перший рядок воркера каже `model demo (demo-rules)`. Якщо так —
висновки про «кмітливість» агента недійсні, валідні лише висновки про harness.

Без провайдера в `apps/.env` воркер зупиняється **одразу** на старті, а не на
першому ході, і підказує офлайн-шлях. Це навмисно: зламаний ключ не має
проявлятися посеред ходу, коли інструменти вже викликані.

## Що з цього автоматизовано

Офлайн-тести покривають те, що запитами перевіряти ненадійно — ліміт
самокорекції, порядок повторів, вичерпання бюджету:

```bash
go test -count=1 ./...                    # ваші контрактні тести офлайн
go test -race ./week4/Day8_Fault_Tolerant_Tool_Harness/...
```

Живий прогін із справжньою моделлю — окремо й за бажанням:

```bash
LAB_LIVE=1 go test -run Live -v .
```

Він перевіряє **інваріанти**, а не слова відповіді: рівно один кейс після двох
збоїв еквайрингу, щонайменше три спроби `OpenRefundCase`, пам'ять відповідає в
новій сесії. Без провайдера тест пропускається й називає причину.
