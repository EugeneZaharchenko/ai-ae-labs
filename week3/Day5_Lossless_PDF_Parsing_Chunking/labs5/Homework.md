# Практичне завдання 5 — Агент вчиться читати: ingestion-конвеєр для бази знань

## Легенда

Ваш майбутній Research Agent має читати документи, а не лише гуглити. Цього тижня ви будуєте йому «травну систему»: ingestion-конвеєр, що приймає складні PDF і нарізає їх на ієрархічні чанки **без втрати структури** — таблиця, розрізана навпіл, отруїть усі майбутні відповіді.

Орієнтир — запит compliance-юриста LEDGERWORKS: *«які знахідки (Findings) з Severity=High пов'язані з Vendor=Acme у звітах SOC2 Type II за Q3 2025?»*. Це — multi-hop запит, який неможливо обробити без втраченої структури таблиць і без entities, що зв'язують Vendor, Report і Finding.

## Навчальні цілі (резонанс із лекцією)

Після виконання ДЗ ви зможете:

1. **Пояснити**, де саме в ланцюжку «PDF → embeddings → відповідь» втрачається таблична структура, і як lossless parsing її зберігає.
2. **Зібрати** на Go ingestion-граф `load → parse → chunk → extract → index_vector → index_graph` як workflow-граф (`workflow.NewFunctionNode` + `workflow.Chain`, без LLM, без API-ключа — канон із минулого тижня).
3. **Реалізувати** Parent-Child chunking із прив'язкою `parent_id` і осмисленими межами (за розділами, а не за токенами).
4. **Продемонструвати**, що таблиці пережили парсинг — через статистику (`tables_preserved: N/N`) і порівняння «до/після» у README.
5. **Застосувати** entity resolution на невеликому корпусі (++ Advanced) із confidence scoring і manual queue.

## Основне завдання

**Ваше завдання —** зібрати `Ontology-Aware Knowledge Builder` як workflow-граф зі стартового шаблону [week3/Day5_Lossless_PDF_Parsing_Chunking/labs5/main.go](https://github.com/dimetron/ai-ae-labs/blob/main/week3/Day5_Lossless_PDF_Parsing_Chunking/labs5/main.go):

1. **Скелет графа** на `workflow.NewFunctionNode` + `workflow.Chain` (канон минулого тижня). Ланцюжок: `Start → load → parse → chunk → extract_entities → index_vector → index_graph → report` — у стартері він уже зібраний у `graph.go`, вузли — заглушки в `pipeline.go`. Кожен вузол — окрема Go-функція з типізованим input/output, як ми робили з `prepare`/`format` у ДЗ 4. Працює без LLM, без API-ключа — тільки локальний код.

2. **Вузол `parse` — lossless парсер.** PDF обов'язково; Markdown як альтернатива для тестування. Стартер уже веде PDF у [docling-mcp](https://github.com/docling-project/docling-mcp) (`internal/docling`) і отримує Markdown із таблицями як таблицями. Це правило курсу: **спеціалізована обробка (ML-парсинг, OCR) — окремий MCP-сервер**, а граф лише викликає його інструменти. Інший конвертер підключайте так само — через `MarkdownConverter`, а не бібліотекою всередині процесу агента. Ваша частина — довести, що це справді lossless на **вашому** PDF: порахуйте блоки (`Blocks: N (8 tables, 12 headings, 22 paragraphs)`) і перевірте, що кожна таблиця ціла, з заголовками стовпчиків. Пастка, яку видно на тестовому PDF: docling сплющує рівні заголовків (і `1 Scope`, і `1.1 Vendors in scope` стають `##`) — ієрархію відновлюйте з нумерації розділів.

3. **Вузол `chunk` — Parent-Child із прив'язкою до ієрархії.** Межі parent chunks — за заголовками розділів (h1/h2). Межі child chunks — за блоками (paragraph, table, list) із обмеженням `MaxChildTokens ≈ 200`. Кожен child має `parent_id` і `section_path` (наприклад, `3.2 Security Findings`). Тест-контракт: жодна таблиця не може бути розрізана між двома children.

4. **Прогон через власний документ.** Візьміть один складний PDF (фінансовий звіт, наукова стаття, security-стандарт — див. альтернативні теми) із щонайменше 2 таблицями і 3 рівнями заголовків. Прогон має завершитися event log'ом, де видно `Parents: N, Children: M, Tables: K/K preserved`.

5. **Статистика у `report` (або в event log вузла `chunk`).** README має містити: кількість чанків за рівнями (parents/children), розміри (min/avg/max у токенах), скільки таблиць збережено цілими. **Це — обов'язковий graded-блок**, бо без нього Оксана не зможе перевірити, чи справді працює lossless.

6. **README з порівнянням «до/після».** Покажіть ту саму таблицю: (а) після naive chunking по 800 токенів (розрізана, клітинки розкидані між 2–3 чанками, заголовки стовпчиків втрачені); (б) після структурного парсингу (ціла, у Markdown, із заголовками). Це — та відповідь, яка переконує аудитора, що наш RAG більше не «leaky».

7. **Юніт-тести вузлів** на `agent.StrictContextMock` (канон минулого тижня). Кожен вузол тестується окремо, табличним тестом, без API-ключа, без мережі. `go test ./...` має бути зеленим.

   Стартувати з нуля не треба: `main_test.go` у стартері вже дає форму — фейк-контекст `nodeCtx` зі вбудованим `agent.NewStrictContextMock`, фейковий конвертер замість docling, табличні тести на `load`, `parse` і `report`, наскрізний `TestGraph_EarlyWin` і контракт-тест `TestChunk_TableStaysWhole`. Ваша робота: (а) зняти `t.Skip` із контракт-тесту й довести його до зеленого реалізацією `chunk`; (б) переписати тести, позначені `TODO(студент)`, — вони навмисно описують поведінку **заглушок** і мають впасти, щойно ви зробите справжню реалізацію; (в) додати тести на `extract_entities` та `index_*`. У критерій «робочий конвеєр» зараховується саме ваш набір тестів, а не наявність файлу зі стартера.

8. **Експорт для ДЗ 6.** Збережіть чанки у JSON (масив `Chunk` — поля фіксує `TestChunkJSONContract`). ДЗ 6 читає саме цей формат: `CHUNKS=шлях/до/chunks.json go run . console`.

## Альтернативні теми (на вибір)

Та сама механіка (ingestion-граф із Parent-Child chunking), інший корпус. Обирайте тему, яка вам ближче, і застосовуйте всі вимоги основного завдання до неї:

- **Security:** chunker для security-стандарту (CIS Benchmark, OWASP ASVS) — кожна вимога = дочірній чанк, розділ = батьківський; таблиці рівнів відповідності зберігаються цілими.
- **Research:** chunker наукових статей arXiv — секції/підсекції як ієрархія, таблиці результатів як атомарні чанки.
- **Finance:** chunker квартальних звітів публічних компаній (10-Q, 6-K) — financials statements, MD&A, footnotes як parent; кожен рядок таблиці = child.
- **Fun:** chunker книги рецептів — рецепт = батько, інгредієнти/кроки = діти; таблиця пропорцій не ріжеться.

Критерії оцінювання — ті самі. Альтернативна тема не дає бонусних балів, але може бути зручнішою для вашого домену.

## ++ Advanced (до 20 балів, для сеньйорів)

Оцінюється понад базові 80 балів. Це **не** 🔥 Бонус-трек — той не оцінюється взагалі (див. нижче).

### A1. Векторний індекс + 5 контрольних запитів по табличних даних (до +10 балів)

Поверх чанків побудуйте справжній векторний індекс (навіть in-memory через стаб-embedding — це зараховується, якщо в README чесно зазначено «deterministic stub embedding»). Виберіть 5 запитів, які спираються **на конкретні числа з таблиць** (наприклад, «який Vendor має Compliance=SOC2 Type II і Findings ≥ 2?»). Для кожного запиту в README: запит → топ-3 retrieved children → відповідь (яку ви обчислюєте вручну з таблиці) → snippet з parent chunk із повним контекстом.

Мета — показати, що **detail-oriented запити по таблицях тепер працюють**, бо таблиця пережила парсинг і потрапила в контекст цілою.

### A2. Entity resolution із confidence scoring + manual queue (до +10 балів)

Реалізуйте повний Бонус-трек із лекції: embedding-based similarity лише пропонує кандидатів. `≥ 0.95` дозволяє canonicalize **лише** за додаткового детерміністичного доказу (затверджений alias, той самий тип); решта пар із `score ≥ 0.85` іде в manual queue, `< 0.85` — відхилити. Підготуйте файл `merge_queue.jsonl` із кандидатами на ручну перевірку. У README опишіть: які пороги ви обрали, який доказ потрібен для canonicalization і скільки кандидатів потрапило в manual queue.

Мета — показати, що автоматизація merge не означає «без контролю»: manual queue — це спосіб поєднати швидкість із якістю.

### A3. Паралельна обробка кількох документів (замість A1/A2, до +10 балів)

Fan-out на кілька `load → parse → chunk` гілок із `JoinNode`-агрегацією (див. `examples/workflow/complex`). Запустіть конвеєр на 5+ документах паралельно, порівняйте час виконання з послідовним варіантом. У README: час послідовно vs паралельно, throughput (документів/хв), спостереження про race conditions (якщо є).

Мета — показати, що workflow-граф масштабується, а не лишається hobby-скриптом.

> **Дозволяється комбінувати A1 + A2 для повного Advanced-бонусу (20 балів), якщо обидва блоки реалізовані якісно. A3 — замість A1+A2, не разом із ними.**

## 🔥 Бонус-трек (не оцінюється, не потрібен для сертифіката)

- **Freshness-сигнал у чанку.** Додайте до frontmatter чанка поле `valid_until` для тарифного розділу LEDGERWORKS і по черзі «прострочте» два чанки: покажіть в eval, що retrieval з metadata-фільтром за свіжістю перестає повертати протухлу ставку. Балів не дає; робиться для себе.
- **O-RAG: зріз схеми під чанк + LLM-екстракція з вільного тексту (Lecture, 🔥 Бонус-трек B).** Потрібна лише локальна модель через Ollama — без API-ключа. Додайте перед `extract_entities` вузол `prefilter_schema`: класи онтології з визначеннями → окремий маленький vector-індекс; для кожного child-чанка — варіанти тексту (оригінал + триграм-вікна; переклад — за бажанням) → cosine top-K класів → зріз схеми (лише ці класи і зв'язки між ними). Далі `extract_llm` зі структурованим виходом за зрізом, і в `index_graph` — два ребра на кожному екземплярі: `extracted_from → chunk_id` і `instance_of → клас`. Що показати в README: на 20 чанках порівняйте «вся онтологія в промпті» проти «зріз» за часткою типів поза онтологією (зі зрізом має бути 0) та precision по `Signer`/`Tariff`; окремо — список відсіяних класів, які потім знадобилися (recall-ризик префільтра). Балів не дає; для десяти класів LEDGERWORKS це свідомо overengineering — ви збираєте механіку, яка окупається на десятках класів.

## Якщо щось не працює

- **`go run . console` не стартує / помилки компіляції.** Спершу `go version` — потрібен **Go 1.27+** (`go`-директива в `go.mod`). Найчастіша плутанина: у документації ADK фігурує `go 1.26.6` — це мінімум *самого ADK*, а не модуля лаб; на Go 1.26.x `go mod tidy` впаде з `go.mod requires go >= 1.27`. Далі `go mod tidy`; якщо помилка вказує на ADK API — звірте сигнатури з [`examples/workflow/`](https://github.com/google/adk-go/tree/v2.4.0/examples/workflow).
- **PDF: `"uvx" not found`.** Встановіть [`uv`](https://docs.astral.sh/uv/getting-started/installation/) або вкажіть свій сервер у `DOCLING_MCP_CMD`. Markdown-файли docling не потребують.
- **PDF: перший запуск «висить».** docling завантажує моделі розмітки (сотні MB) — прогрес видно в stderr. Наступні запуски — секунди.
- **PDF: `DOCLING_MCP_SERVICE_URL is not set`.** docling-mcp 3.x за замовчуванням конвертує віддалено. Стартер сам ставить `DOCLING_MCP_CONVERSION_MODE=local`; якщо ви перевизначили `DOCLING_MCP_CMD`, запускайте пакет із `[local]` (`uvx --from='docling-mcp[local]' …`).
- **Парсер не показує таблиці в Markdown.** Перевірте magic bytes `%PDF` — сканований PDF без текстового шару потребує OCR: `DOCLING_MCP_DO_OCR=true` (стартер вимикає OCR за замовчуванням; OCR завантажує ще моделі). Якщо PDF текстовий, а таблиця не розпізналась (merged cells, таблиця-картинка) — зафіксуйте це в README як обмеження.
- **`Tables: K/K preserved` менше за очікуване.** Event log показує вузол-порушник: parse повернув менше — не витяг парсер; parse повернув усі, chunk повернув менше — chunker розрізав таблицю (падає тест-контракт «таблиця не ріжеться»).
- **`vectors_added` ≠ `len(children)` або `nodes_added` > `len(entities)`.** Перше — помилка індексації (пропущений child або подвійне додавання); друге — дублікати сутностей: entity resolution не спрацював або gazetteer занадто вузький.
- **Порожній `merge_queue.jsonl` в A2.** Не завжди добре: можливо, gazetteer не генерує кандидатів. Додайте відомі дублі («Acme Bank» / «ACME Bank JSC») у тестовий корпус і переконайтеся, що вони з'являються в черзі.

## Обмеження та чесні застереження

- **PDF парсери не ідеальні.** docling добре тримає звичайні таблиці, але merged cells, таблиці-картинки й нестандартні шрифти — ризик для будь-якого парсера. У README чесно зазначте обмеження: «які типи таблиць підтримуються, які — ні, що робите, коли парсер не витягнув таблицю (fallback)». Якщо обираєте інший парсер (Go-бібліотеку чи Docling Serve), замініть `MarkdownConverter` у `pipeline.go` — граф від цього не зміниться.
- **Embedding у лабі — стаб.** У базовому завданні немає реального embedding: child chunks зберігаються в in-memory структурі, яка імітує vector store. Якщо ви додаєте реальний embedding (A1) — зазначте, яку модель використовуєте (локальну чи хмарну) і чи вона детерміністична.
- **In-memory graph.** Knowledge graph у базовій лабі живе у вашій in-memory adjacency map. Перезапуск процесу = втрата графу. Для продакшну — окреме сховище; це поза межами ДЗ, але варто зазначити в README.
- **Provenance переживає merge.** Для кожної сутності й зв'язку збережіть `document_id`, `page_no`, `chunk_id`/`source_chunk_id`; під час merge об'єднайте, а не перезапишіть посилання на джерела. Це дає аудитору шлях до кожного первинного фрагмента.
- **Сканований PDF — окремий передкрок.** Якщо у файлі немає текстового шару, спершу потрібен OCR/VLM-OCR; не називайте результат `Tables: K/K preserved`, доки не перевірили його на оригінальній сторінці.
- **Entity resolution (A2) — не магія.** Якість сильно залежить від gazetteer-списків і embedding-моделі. Якщо ваш merge queue порожній — це не завжди добре, це може означати, що gazetteer надто вузький. Тестуйте на відомих дублях.

Альтернативна тема оцінюється за тими самими критеріями. **Базового завдання достатньо для сертифіката; «🔥 Бонус» ніколи не є його умовою.** Бали за всі 12 завдань підсумовуються: від 60 % відкривається генерація сертифіката, від 85 % — з відзнакою.

## Формат здачі

GitHub-репозиторій з кодом, тестовим документом (або посиланням на нього) та README. Обов'язкові артефакти в репозиторії:

- `main.go` — тонка точка входу; `graph.go` — граф через `workflow.Chain`.
- `pipeline.go` (або по файлу на вузол: `load.go`, `chunk.go`, …) — вузли конвеєра.
- `*_test.go` **поруч із кодом** — табличні тести на `agent.StrictContextMock` для кожного вузла + контракт-тест на «таблиці не ріжуться». (Окрема тека `tests/` не бачить неекспортованих функцій `package main`.)
- `testdata/` — ваш тестовий PDF (або скрипт для його завантаження) і `chunks.json` — експорт для ДЗ 6.
- `README.md` — інструкція запуску, статистика, порівняння naive vs структурний, приклад запиту.
- `merge_queue.jsonl` (тільки якщо робите A2).

`go build ./...` має проходити; `go test ./...` має бути зеленим. Посилання на репозиторій — у форму здачі. Якщо репозиторій закритий — додайте акаунт ментора в collaborators (акаунт указано в інструкції до курсу на платформі).
