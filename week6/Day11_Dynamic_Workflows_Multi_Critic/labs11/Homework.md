# Практичне завдання 11 — Цикл до зеленого: динамічний граф із командою критиків

## Легенда

Ваша команда з ДЗ 10 вміє працювати паралельно й питати дозволу. Тепер вона навчиться **не випускати брак**: maker пише, критики перевіряють, і цикл крутиться, доки робота не пройде перевірку — або не вичерпається бюджет ітерацій. Це останній механізм, якого бракує фінальному Research Agent.

Сценарій: у LEDGERWORKS bug #423 у billing service живе третій тиждень; Ірина чекає на результат до понеділкової ради. Ваш мульти-кодинг-агент — це спроба зробити за день те, на що людина витрачала тиждень. Але «спроба» — це не «один прогін LLM»; це *цикл* із об'єктивною перевіркою, кількома критиками й обмеженим бюджетом.

## Ранній win: перший видимий результат за ≤15 хвилин

Перший видимий результат — без API-ключа, до того, як ви напишете хоч рядок власного коду:

1. З кореня репозиторію виконайте `go test ./week6/Day11_Dynamic_Workflows_Multi_Critic/labs11/solution/...`.
   **Чекпойнт:** тести зелені (`ok`), серед них — «сходиться на третій спробі після фідбеку грейдера»: перші дві спроби зупиняє детермінований грейдер, третя проходить. Це весь цикл maker → critics → feedback, без ключа.
2. Відкрийте стартовий шаблон `week6/Day11_Dynamic_Workflows_Multi_Critic/labs11/main.go` і виконайте `go build ./...`.
   **Чекпойнт:** збірка проходить — скелет динамічного вузла, типи `Draft`/`Verdict` і заглушки на місці.

Далі — ваша робота: замінити заглушки на реальні вузли за пунктами нижче.

## Основне завдання

**Ваше завдання —** зібрати `Multi-Critic Coding Agent` як динамічний граф, стартуючи з [week6/Day11_Dynamic_Workflows_Multi_Critic/labs11/main.go](https://github.com/dimetron/ai-ae-labs/blob/main/week6/Day11_Dynamic_Workflows_Multi_Critic/labs11/main.go):

1. **Цикл maker/checker у `workflow.NewDynamicNode`.** `generate` (пише/виправляє Go-функцію за завданням та зауваженнями критиків) → **компілятор/тести спершу** → критики (див. п. 2) → якщо хоча б один критик `Passed=false`, його `Comments` додаються в `Draft.Feedback` і передаються в `generate` на наступній ітерації; цикл завершується, коли **всі** критики `Passed=true`, або коли `maxAttempts` вичерпано. Помилка `budget exhausted` повертається як подія в event log.
2. **≥3 критиків із різними фокусами.** Один — обов'язково **об'єктивний** (компіляція/тести через `go build`/`go test` як інструмент, з `context.WithTimeout` 10–15 с на виклик). Решта — LLM-критики (стиль/ідіоматичність, продуктивність, security) із різними system prompts. Кожен повертає типізований `Verdict{Critic, Passed, Comments}` із заповненим полем `Critic` для аудиту.
3. **Валідація схем вердиктів.** Несумісна відповідь критика (невідомий `Critic`, або `Passed=true` з непустими `Comments`, або відсутні required-поля) **відсікається** на вході в агрегатор, а не «якось інтерпретується». Помилка валідації — це не «ігнорувати й продовжити», а «помітити в event log і зупинити цикл» (варіант: «помітити і вважати вердикт `Passed=false` із системним коментарем»).
4. **Eval-звіт трьох ранів на різних задачах** (однаковий `maxAttempts`, наприклад 4): тести пройдено / кількість ітерацій / час / вартість у токенах з `UsageMetadata` (разом із thinking-токенами) — таблиця в README. Задачі — три реальні billing-задачі LEDGERWORKS (`prorate_refund`, `parse_amount`, `validate_iban`), кожна з власним тест-файлом і власним `Holdout`. Головна цифра звіту — **false accepts**: скільки разів цикл прийняв кандидата, який на `Holdout` виявився хибним.
5. **Event log читається.** У README додайте один реальний зріз event log з одним із ранів (згенерований `go run ./week6/Day11_Dynamic_Workflows_Multi_Critic/labs11 -task prorate_refund 2>&1 | tee /tmp/eventlog.txt`), де видно: кожну ітерацію `generate`, кожен вердикт, рішення гейта на кожній спробі (ключі `w6p1:attempt:<N>`), фінальний emit `loop_done` або помилку `budget_exhausted`.

## Альтернативні теми (на вибір)

Та сама механіка (динамічний цикл + ≥3 критики + об'єктивна метрика), інший домен:

- **Security:** критики конфігів Kubernetes — критик привілеїв (`runAsNonRoot`, `readOnlyRootFilesystem`), критик ресурсних лімітів (`resources.limits`), критик секретів (наявність `env.valueFrom.secretKeyRef` без `optional: true`); об'єктивна метрика — `kubeconform` або власний валідатор.
- **Research:** критики дослідницької записки — критик фактів (кожне твердження має джерело з ДЗ 6), критик структури (наявність вступу/висновку/секцій), критик стилю (абзаци ≤ 5 речень); метрика — чекліст-валідатор.
- **Fun:** критики меню — шеф пише рецепт, критик бюджету (сума інгредієнтів), критик калорій і критик «це взагалі смачно?» ганяють його по колу. Об'єктивна метрика — парсинг інгредієнтів і підрахунок суми.

## ++ Advanced (до 20 балів, для сеньйорів)

- **Паралельні критики.** Зробіть fan-out усіх критиків. `JoinNode` застосовуйте лише в окремому статично оголошеному підграфі; всередині dynamic node — конкурентні `workflow.RunNode(..., workflow.WithUseSubBranch())` або `NewParallelWorker`. Заміряйте послідовний vs паралельний варіант на 3 задачах; не обіцяйте «рівно у 3 рази» — замір залежить від latency і лімітів провайдера.
- **Тести без моделі + per-node таймаут.** Табличні тести `ParseVerdict`/`ValidateVerdict` (невідома роль, підміна ролі, провал без коментаря, проза до/після JSON) — без LLM, без мережі. Критик — це `llmagent`, тож `agent.StrictContextMock` тут **не** допоможе (він для чистих `FunctionNode`, як ваш гейт); наскрізні тести циклу — через `fakellm.New(...)` + `labrun.Run(...)`. `workflow.NodeConfig.Timeout` на вузол гейта (у лабі `gateTimeout = 90 с`) і на сам вузол циклу — `loopTimeout(maxAttempts)`, більший за суму того, що всередині.

## 🔥 Бонус-трек (не оцінюється, не потрібен для сертифіката)

Виклик зі слайда — **не оцінюється, не потрібен для сертифіката**: додати `critic_static_analysis` як четвертий вузол — `gofmt -l` + `go vet` + `staticcheck`. У README порівняйте `tests_passed` проти `tests_passed && static_clean`; якщо різниця > 30% — у вас є реальна проблема з якістю коду, який генерує агент.

## Якщо щось не працює

- **Цикл «не сходиться», хоча код виглядає правильним** — див. FAQ №16: перевірте, що гейт реально доходить до стадії `test` (а не зупиняється на поблажливому `vet`), що код пишеться в правильний пакет, і що `Draft.Feedback` з коментарів критиків справді передається в `generate` на наступній ітерації.
- **`go build` / `go run` падає на старті** — `go version` має бути **≥ 1.27.1** (стільки вимагає `go.mod` репозиторію `ai-ae-labs`; на 1.25/1.26 збірка впаде з `go.mod requires go >= 1.27.1`), `go mod tidy` без помилок. Якщо `NewDynamicNode` не компілюється — звірте сигнатуру з [`examples/workflow/dynamic/basic/main.go`](https://github.com/google/adk-go/blob/main/examples/workflow/dynamic/basic/main.go) у публічному репозиторії ADK Go (FAQ №19).
- **LLM-критики повертають помилку авторизації** — базовий шлях працює без ключа: LLM-критики лишаються заглушками з `Passed=true`, блокером виступає лише об'єктивний критик. Ключ у `.env` потрібен тільки для реальних LLM-вердиктів.
- **Гейт «зависає»** — перевірте `StageTimeout` усередині `gate.Runner.Grade` і зовнішній `NodeConfig.Timeout` на вузлі гейта; при таймауті репорт має бути `gate.Report{OK: false, Stage: "gate"}`, а не вічне очікування (FAQ №12).
- **Валідація пропускає сміття** — негативний тест обов'язковий: підкладіть вердикт із невідомим `Critic` і переконайтеся, що цикл зупиняється з позначкою в event log, а не «якось інтерпретує» відповідь.

## Критерії оцінювання

| Критерій | Бали |
|---|---|
| Динамічний цикл виправлень до «зеленого» стану з лімітом `maxAttempts` | 30 |
| ≥3 критики з різними фокусами, один — об'єктивний (`go build`/`go test`) | 25 |
| Валідація схеми вердиктів (несумісний вердикт відсікається, не «ігнорується») | 15 |
| Eval-звіт (3 рани: ітерації/час/результат) + event log у README | 10 |
| ++ Advanced (паралельні критики / юніт-тести / per-node таймаути) | 20 |
| **Разом** | **100** |

Базове завдання дає до 80 балів; ++ Advanced — **+20 додаткових балів** для сеньйорського треку (разом 100). Він ніколи не є передумовою сертифіката: джуніор завершує базовий артефакт без API-ключа, використовуючи детерміновані заглушки й тести. 🔥 Бонус-трек не оцінюється взагалі. Альтернативна тема оцінюється за тими самими критеріями.

> **Зв'язок із курсом:** цей агент — база для фінального Вебінару 12 (self-improving coding agent за паттерном `karpathy/autoresearch`). Ваш код із ДЗ 11 має бути готовий до того, щоб обмежити поверхню змін (один файл), додати окремий артефакт стратегії та формалізувати метрику фітнесу.
