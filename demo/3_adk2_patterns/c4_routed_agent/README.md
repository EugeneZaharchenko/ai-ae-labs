# C4 · Routed Agent

**Хто вирішує наступний крок:** код · **Категорія:** C · маршрутизований агент

Ваша функція маршрутизації обирає рівно одного агента на виклик (рівні моделей:
дешева / сильна), а якщо обраний агент упав, не віддавши жодного виводу, —
перемикає на запасний.

> **`RoutedAgent` і `AgentRouter` у ADK Go v2.4.0 не існують.** Джерело каталогу
> позначає їх як TypeScript v1.0.0, experimental. Тут — Go-конструкція: динамічний
> вузол тримає правило маршрутизації й failover у звичайному Go і запускає агентів
> через `workflow.RunNode`.

```
router (DynamicNode) ─ правило ─→ cheap_agent  ─✗ помилка → strong_agent
                               └→ strong_agent ─✗ помилка → cheap_agent
```

## Запуск

```bash
go run .                                        # збій дешевого рівня → failover
go run . -input "What is my data limit?"        # дешевий рівень, без failover
go run . -input "Please compare plans A and B"  # сильний рівень за правилом
go run . -live                                  # та сама конфігурація на моделі з apps/.env
go run . console                                # діалог у консолі
go run . web api webui                          # Web UI на http://localhost:8080/ui/
```

Очікуваний слід офлайн-демо:

```
🤖 strong_agent: [strong_agent] answer to: What is my data limit? (simulate outage)
⚙️  router ⇒ {"answer":"[strong_agent] …","agent":"strong_agent","failover":true}
```

Невдалої спроби `cheap_agent` у сліді немає: модель упала до першої події, тому
користувач нічого часткового не побачив — саме тому failover тут безпечний.

## Go-примітиви (ADK Go v2.4.0)

| Примітив | Роль у демо |
|---|---|
| `workflow.NewDynamicNode[IN,OUT]` | роутер: правило рівня + failover у Go-коді |
| `workflow.RunNode[OUT](ctx, child, input)` | запуск обраного агента; помилка дитини повертається як `error` |
| `workflow.ErrNodeFailed` | сентинел, яким `RunNode` обгортає збій дитини |
| `workflow.NodeConfig.RetryConfig` | сусідній інструмент: повтор **того самого** вузла, а не перемикання |

## Коли брати

Інфраструктурна турбота, а не робочий процес: перемкнутися на іншого провайдера
при помилці, розділити трафік для A/B-тесту, відправляти прості запити дешевій
моделі, а складні — дорогій.

## Коли не брати

Для маршрутизації **задач** — це [B4](../b4_conditional_route/) або
[C1](../c1_coordinator/).

## Що подивитися в коді

- `tier` — правило маршрутизації: код, а не виклик моделі. Це і відрізняє C4
  від C1.
- `route` — failover. Він коректний лише тому, що помилка моделі стається до
  будь-якого виводу. Якщо агент уже віддав частину відповіді, перемикання дало б
  користувачу дві різні половини — такий збій треба віддавати далі, а не
  ретраїти.
- `RunNode` не зберігає значення помилки дитини: вона перетинає планувальник як
  текст, тож `errors.Is(err, workflow.ErrNodeFailed)` — так, а
  `errors.Is(err, errOutage)` — ні. Розрізняти типи збоїв доводиться за
  повідомленням або на рівні `model.LLM`.
- У `-live` обидва рівні отримують ту саму модель з `apps/.env`, тож failover не
  спрацює — щоб побачити справжні рівні, потрібні дві різні моделі.
